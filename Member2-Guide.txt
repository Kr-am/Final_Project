WORK PACKAGE B - WITHDRAWAL PROCEDURE (HOUR 1-3)
Implement DoWithdrawal as a NEAR procedure:
[ ] Verify a valid logged-in account index (0..9).
[ ] Read RequestedAmount from Member 1's numeric helper or common input.
[ ] Reject zero, text that failed parsing, >30,000 centavos.
[ ] Load Balances[CurrentIndex] using 2*index byte offset.
[ ] Reject amount > current balance (insufficient funds).
[ ] Load DailyWithdrawn[CurrentIndex]. Reject withdrawal when
    currentDaily > 60,000 - amount; this avoids overflow too.
[ ] ONLY after all checks pass:
        Balances[index] = oldBalance - amount
        DailyWithdrawn[index] = oldDaily + amount
[ ] Set TxnType='W', TxnSourceID=account ID, TxnDestID=0,
    TxnAmount (or RequestedAmount), TxnResultBalance=new balance,
    TxnStatus=1 and TxnError=0.
[ ] Call AppendTransaction once on success, followed by
    UpdateFraudAfterSuccess once.
[ ] On rejection do NOT change balance/daily withdrawn/fraud streak;
    set TxnStatus=0, correct TxnError, resulting balance=unchanged,
    increment RejectedCount once, call AppendTransaction once.
[ ] Print clear errors: invalid amount, insufficient funds, daily cap.
[ ] Check boundary cases: amount=1, amount=30,000, exact daily cap,
    amount=0, and 1 centavo over allowed remaining daily cap.

WITHDRAWAL PSEUDOCODE
  INPUT amount
  PREPARE transaction context
  IF amount invalid OR amount > MAX_AMOUNT: REJECT
  IF balance < amount: REJECT
  IF dailyWithdrawn > DAILY_LIMIT - amount: REJECT
  newBalance = balance - amount
  newDaily = dailyWithdrawn + amount
  COMMIT both values
  set accepted transaction status, log, update fraud state, show success
  EXIT
  REJECT: preserve original values, count and log rejection, show reason

WORK PACKAGE C - TWO-PHASE TRANSFER PROCEDURE (HOUR 2-4)
Implement DoTransfer for source = logged-in account, destination = entered ID.
PHASE 1 - VALIDATE ONLY (no balance updates):
[ ] Confirm source logged in and destination exists via FindAccount.
[ ] Verify source index and destination index are different.
[ ] Reject amount that is zero/invalid/>30,000 centavos.
[ ] Check source balance >= amount.
[ ] Check destination balance <= 65,535 - amount.
[ ] Check operation limits (maximum per transfer; daily cash-withdrawal
    cap does not apply to outgoing transfers under proposed rules).
[ ] Populate TxnType='T', TxnSourceID, TxnDestID, TxnAmount, status/error
    in a consistent way, including destination ID on failed lookups.

PHASE 2 - COMMIT (only after all validations succeed):
[ ] Compute newSource = sourceBalance - amount.
[ ] Compute newDest = destBalance + amount.
[ ] Store newSource and newDest; no early partial writes.
[ ] Set TxnResultBalance to newSource (source after the transfer),
    TxnStatus=1, TxnError=0.
[ ] Call AppendTransaction exactly once.
[ ] Call UpdateFraudAfterSuccess to reset streak on BOTH affected accounts.
[ ] Print success with source/destination IDs and results.

REJECTION PATH:
[ ] NEVER modify EITHER account's balance on a failed transfer.
[ ] Do not change daily counters or fraud streaks on failed transfers.
[ ] Increment RejectedCount exactly once.
[ ] Set TxnStatus=0; record error and unchanged source balance;
    log the attempt exactly once if the session account is known.
[ ] Display reason: invalid destination, same account, insufficient
    funds, transfer limit, or destination balance overflow.

TRANSFER PSEUDOCODE
  INPUT destination ID, amount
  PREPARE transaction context
  IF source/destination invalid OR equal: REJECT
  IF amount invalid OR amount > MAX_AMOUNT: REJECT
  IF sourceBalance < amount: REJECT
  IF destBalance > 65535 - amount: REJECT
  newSource = sourceBalance - amount
  newDest = destBalance + amount
  // Only here are the two balances changed
  sourceBalance = newSource
  destBalance = newDest
  log success, reset both fraud streaks, show result
  EXIT
  REJECT: log failure and show reason; both balances unchanged

IMPORTANT: DO NOT implement a transfer as a call to DoWithdrawal followed
by DoDeposit. That can deduct the source account before destination checks,
create inconsistent balances, affect daily withdrawal totals incorrectly,
and produce two logs for what should be one transfer.
